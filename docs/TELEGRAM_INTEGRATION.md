## What was verified

### 1. Initialization and ordered asynchronous updates

TDLib is asynchronous. The official getting-started guide says the first authorization state is `authorizationStateWaitTdlibParameters`; the client must answer it with `setTdlibParameters`. The JSON interface provides `td_create_client_id`, `td_send`, `td_receive`, `td_execute`, and the older per-client `td_json_client_*` functions. TDLib's client documentation requires that one receiver consumes updates and that updates/responses are applied in receive order.

TeleDrive uses the official **JSON-Java** interface generated by the Android build (`org.drinkless.tdlib.JsonClient`). A single coroutine on `Dispatchers.IO` calls `receive` and publishes updates in order. Requests include an `@extra` correlation value. The adapter never calls `receive` from multiple threads and never waits on the main thread.

`setTdlibParameters` will set:

- `use_test_dc = false` for production builds unless a deliberately configured test build is used;
- an app-private `database_directory` and `files_directory`;
- a 32-byte database encryption key protected by Android Keystore;
- Android/system/application metadata;
- the configured `api_id` and `api_hash`;
- `use_file_database = true`, `use_chat_info_database = true`, and `use_message_database = true` so TDLib can persist its own Telegram state and downloaded/uploaded file knowledge across restarts.

No TDLib logs, request payloads, phone numbers, codes, passwords, captions, or file contents are forwarded to the app logger.

### 2. Supported user authorization states

The documented authorization state hierarchy includes:

- `authorizationStateWaitTdlibParameters`
- `authorizationStateWaitPhoneNumber`
- `authorizationStateWaitCode`
- `authorizationStateWaitPassword`
- `authorizationStateWaitEmailAddress`
- `authorizationStateWaitEmailCode`
- `authorizationStateWaitOtherDeviceConfirmation`
- `authorizationStateWaitRegistration`
- `authorizationStateWaitPremiumPurchase`
- `authorizationStateReady`
- `authorizationStateLoggingOut`, `authorizationStateClosing`, and `authorizationStateClosed`

The adapter maps all of these to an app-level state. The UI supports phone number, authentication code, password, email address/code, and registration prompts where TDLib exposes them. Registration and premium-purchase states are shown as supported-by-TDLib-but-not-completable-in-this-MVP states rather than being silently skipped. The app can send `setAuthenticationPhoneNumber`, `checkAuthenticationCode`, `checkAuthenticationPassword`, `setAuthenticationEmailAddress`, and `checkAuthenticationEmailCode` without persisting the sensitive values.

A `authorizationStateReady` update is the only state in which the storage repository exposes remote file operations. `logOut` is explicit; it logs out of the TDLib session and leaves Telegram cloud messages untouched.

### 3. Discovering Saved Messages without a hardcoded chat ID

The current user is obtained with `getMe`. TDLib models Saved Messages as the private chat with that current user. TeleDrive therefore calls `getChat(user.id)` after authentication and verifies the returned chat is the expected current-user private chat. It does **not** hardcode a numeric chat ID. If this discovery fails, the app surfaces an integration error rather than guessing.

Newer TDLib versions also expose Saved Messages topic APIs (`loadSavedMessagesTopics`, `getSavedMessagesTopicHistory`, and `searchSavedMessages`). The MVP's library index uses the main Saved Messages chat history with topic id `0`; topic-specific history is an explicit follow-up because topic UX and message relationship handling need separate product decisions. This is documented rather than pretending that topic pagination is already complete.

### 4. History pagination and file-bearing messages

`getChatHistory` returns messages in reverse chronological order. Its documented `limit` is positive and at most 100; `from_message_id = 0` starts at the newest message, and subsequent pages use the last returned message ID. The repository exposes a cursor-based page and stops when TDLib returns no messages or no cursor progress.

The mapper recognizes the file-bearing message content types that TDLib exposes with enough metadata for a file manager:

- `messageDocument` -> `document.document`, document filename, MIME type, size, and TDLib file id (including PDFs, ZIPs, and other general documents);
- `messagePhoto` -> the largest returned `photoSize.photo` file and a generated display name when no filename exists;
- `messageVideo` -> `video.video` metadata;
- `messageAudio` -> `audio.audio` metadata and original filename when present;
- `messageAnimation` -> `animation.animation` metadata;
- `messageVoiceNote` -> `voice_note.voice`;
- `messageVideoNote` -> `video_note.video`;
- `messageSticker` -> `sticker.sticker`, intentionally supported as an image-like file.

The JSON field names above are the official TDLib object fields, not a generic `file` guess. `messageText`, links, service messages, unsupported content, protected content, and malformed JSON are ignored as files but do not abort a page. Every normalized item retains `chat_id` and `message_id` as its remote identity so local actions cannot accidentally target a different message. TDLib's own cache path is never treated as a TeleDrive offline copy; the app-managed storage layer makes that distinction explicit.

### 5. Uploading a document

The adapter sends `sendMessage` to the discovered Saved Messages chat with `inputMessageDocument` and an `inputFileLocal` path. The app's SAF upload flow first obtains a URI, attempts persistable read permission when offered, and streams/copies the URI into an app-private staging file without loading the whole file in memory. The original display name and MIME type are supplied as document metadata; the staged bytes are not transformed.

TDLib's `updateFile` updates contain a `file` object and its `local`/`remote` information. Upload progress is derived from TDLib's reported sizes and never from a timer. `updateMessageSendSucceeded` replaces the temporary message identity with the final message identity; `updateMessageSendFailed` is mapped to a user-safe error and retry eligibility. A cancellation request is best effort: TDLib exposes an explicit `cancelDownloadFile` for downloads, while outgoing message sending is represented by message send state; for an in-flight upload TeleDrive removes the temporary outgoing message when TDLib permits it and documents that the network request may already have completed.

### 6. Downloading a file and progress

For a normalized remote file, TeleDrive calls `downloadFile(file_id, priority, offset, limit, synchronous=false)`. TDLib documents that completion and progress arrive through `updateFile`. The adapter uses `file.local.downloaded_size` relative to the known remote size for progress, distinguishes `is_downloading_active` from `is_downloading_completed`, and returns the TDLib-managed local path only to the app layer after completion. It calls `cancelDownloadFile(file_id, only_if_pending=false)` for cancellation.

The app then copies the completed TDLib output into `files/downloads/<stable-id-hash>/` through a UUID-named `.part` file, flushes it, verifies the expected byte count, and publishes it before marking Room `localAvailability = AVAILABLE`. Startup and worker reconciliation clear missing/corrupt records; stale `.part` files are aged out. Room transfer rows and a unique connected-network WorkManager drain recover queued, failed, and process-interrupted transfers. A completed full history scan reconciles indexed remote IDs that no longer appear as permanent remote deletions while retaining local managed bytes; incremental/incomplete scans do not make destructive absence assumptions. Concurrent requests for the same remote identity share one in-process download operation.

The app never exposes a private filesystem path directly to another app. A managed file is opened/shared through a validated `FileProvider` content URI, with MIME fallback from the sanitized filename. PDF, audio, and video playback use an installed Android viewer/player as the documented fallback when no built-in renderer is present. Explicit export copies bytes to a user-selected SAF destination; the user controls replacement behavior in that provider.

### 7. Deleted, unavailable, and protected files

`updateDeleteMessages` contains `chat_id`, message IDs, and whether deletion is permanent or cache-only. The adapter emits only permanent deletions to the index layer; cache-only removals do not mark a remote message deleted. Room marks a matching record `DELETED` while retaining any verified app-managed local copy. The adapter does not silently turn a missing TDLib cache path into an app-managed file. A `file.local.can_be_downloaded = false`, protected content, a missing remote file, or a TDLib `Error` is surfaced as unavailable; it is not shown as a successful local copy. Removing an app-managed local copy only removes that file and clears its Room fields; it never calls `deleteMessages`.

Remote deletion is an explicit, confirmed action. It calls `deleteMessages(chat_id, [message_id], revoke)` only after confirmation and uses the message properties/available deletion semantics returned by TDLib. The user is told that the message is part of their actual Saved Messages. If a local app-managed copy exists, it remains available until the user separately removes it, so remote and local deletion cannot be confused.

### 8. TDLib database, file database, and application metadata

These are separate stores:

1. **TDLib database:** Telegram session, chat/message cache, and file knowledge under the app-private TDLib database directory.
2. **TDLib files directory:** TDLib-managed downloaded/uploaded file data; it can be optimized or cleared without deleting the remote message.
3. **TeleDrive Room database:** normalized file index, virtual folders, favorites, transfer records, and sync bookkeeping.
4. **TeleDrive DataStore:** non-sensitive preferences such as theme/view/sort and a metadata device ID.
5. **Android Keystore:** protects the TDLib database encryption key wrapper. Authentication codes/passwords are not stored in any of these stores.

Logout closes/logs out the TDLib authorization state. It does not delete the user's Telegram messages or claim to erase every TDLib file automatically; the settings screen offers local cache cleanup separately.

### 9. Metadata synchronization strategy

Telegram Saved Messages has no ordinary filesystem folder API. TeleDrive uses append-only, reserved, versioned **text messages** as an application-level metadata event log. Each record has a deliberately recognizable prefix, schema version, device ID, monotonic device sequence, operation, and payload. The record is encoded with URL-safe Base64 JSON so arbitrary folder/file names—including Amharic and other Unicode scripts—round-trip without being interpreted as markup.

- TeleDrive ignores records with the reserved prefix when building the file library.
- It never edits or deletes an existing user-created message to make room for metadata.
- Local folder/favorite changes are written as new metadata messages when the user enables synchronization.
- On another device, valid records are merged deterministically by `(sequence, device_id, operation_id)`; duplicate operation IDs are idempotent.
- Unknown schema versions, invalid Base64/JSON, missing required fields, and malformed operations are ignored and reported as a non-fatal sync warning.
- A deleted remote metadata message can make metadata unavailable; the local index remains usable and can be rebuilt from remaining records.

This is **eventual, best-effort metadata synchronization**, not an atomic multi-device database. Concurrent edits can resolve by last deterministic event order rather than intent. The UI and privacy documentation state that folder/favorite changes are not guaranteed to be instantly visible across devices. Remote file messages remain untouched by metadata sync.

### 10. File sizes, limits, API credentials, and terms

TeleDrive does not hardcode a Telegram cloud quota or promise a maximum size that is not supplied by TDLib for the current account/build. TDLib and Telegram can impose account, API, rate, upload, download, and concurrency limits that change independently of this app. The app bounds its own queue concurrency and maps rate-limit/network errors to retryable UI states.

Telegram requires each third-party client to use its own `api_id`/`api_hash`; the official API-creation page warns that sample IDs are not suitable for end-user distribution. Users must be told that the app uses the Telegram API and complies with Telegram's API Terms. No bot token or Telegram Web automation is used.

## Native Android integration

The official TDLib Android example at the selected commit builds TDLib from source. It documents Android SDK platform 34, CMake 3.22.1, an Android NDK, OpenSSL, and the `Java`, `JSON`, or `JSONJava` interfaces. TeleDrive selects `JSONJava` so only the small official `JsonClient.java` binding is checked in; the generated native library is supplied by the build step, not replaced with a fake implementation.

Run the repository helper after installing the prerequisites:

```bash
./tools/build-tdlib-android.sh
```

The helper pins the official TDLib commit, runs the upstream Android build path with the JSON-Java interface, and copies only the resulting `tdlib/libs/<abi>` libraries into the ignored `core/telegram/src/main/tdlib/jniLibs/` directory. The selected source commit and ABI list are recorded in `tools/TDLIB_VERSION`. A build without those libraries can compile the Kotlin/Java code and launch its onboarding screen, but live Telegram connection intentionally fails with a clear native-library configuration error; it is not a fabricated offline success.

## App-level reliability behavior

Transfer rows are persisted in Room. Upload staging paths are retained for retryable failures, while successful and explicitly canceled uploads remove their temporary source only after the remote result and any managed-copy attempt have been handled. Explicit cancellation calls the gateway boundary first, waits for the foreground coordinator to settle, then marks the row `CANCELED`; a process/lifecycle interruption instead retains the staged source for recovery. Retryable failure backoff is represented in the transfer record, and a unique WorkManager job resumes queued/due work when Android grants a connected-network window, including process-interrupted `RUNNING` rows. The worker never promises indefinite execution: Android can stop or defer background work, Telegram authorization can expire, and a non-retryable error remains visible for an explicit user retry. Downloads and uploads expose TDLib-reported progress and cancellation; a timer is never used as completion evidence.
